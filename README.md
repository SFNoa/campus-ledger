### 发现并修掉的 5 个 bug

这五个都是**单元测试和编译都发现不了、只有真正跑起来才会暴露**的问题：

1. **提示对话框关不掉（最严重）** `HomeScreen` 里 message/error 两个 `AlertDialog` 的
   `onDismissRequest` 和按钮回调都写成了空 lambda `{ }`，导致弹过一次提示后整个界面被永久挡住、
   只能杀进程。修好后补了两条回归测试，断言的是「点了好/知道了会回调 dismiss」，
   而不只是「对话框弹出来了」。
2. **「手动记一笔」对话框比屏幕高**，保存按钮被挤出可视区且 `verticalScroll` 不起作用
   （因为 Surface 没有高度约束）。加了 `fillMaxHeight(0.92f)`，现在小屏上可以滚动到保存按钮。
3. **重启后余额显示成「—」**：`CardInfo` 只在内存里。改为同步时把 `queryCard` 的权威余额
   落进 `meta` 表，重启后显示「上次同步的余额」，数值与卡内真实余额一致。
4. **同一个 App 会话里第二次同步必失败**（用户上报）。
   提示「登录页结构变了：找不到 id=pwdFromId 的表单」。
   根因：`CookieManager` 是**进程级**的，第一次登录成功后 CAS 会话仍有效，
   第二次 GET 登录页会被 CAS **直接 302 送回 ecard** 并带上新的 `synjones-auth`，
   页面里根本没有账号密码表单，而老代码在那一步直接抛异常。
   改为**复用已有会话**（少一次密码交换，对风控也更友好）。
   顺带修正 `logout` 也要丢掉 CAS 会话 cookie —— 否则「退出」后输错密码也能进去。
   回归测试：`CasSessionReuseTest`（离线 9 项）+ `EcardLiveIT` 里的「连续两次登录」。
   *这个 bug 之所以一直没被发现，是因为我每次连续测试之间都 force-stop 过，
   等于每次都是新进程、干净 cookie，永远是「第一次登录」——测试设计上的盲区。*
5. **失败提示误导**：判断「是否已跳到校园卡站点」时用的是
   `res.url.contains("ecard.csu.edu.cn")` 子串匹配。但登录失败时响应仍停在 CAS 域，
   而其 `service` 查询参数里就编码了 ecard 域名（`...%2F%2Fecard.csu.edu.cn%2F...`），
   子串命中 → 把「密码错误」误判成「登录成功但没取到 token」，让人完全找不到方向。
   改为比较 **host**，现在会如实显示 CAS 返回的原因（如「您提供的用户名或者密码有误」）。

**仍然只有你的真机能做的：** 在你自己手机上装一次。
模拟器是真实的 Android 运行时，但严格说不是「真机」——屏幕尺寸、厂商 ROM、真实网络环境
（校园网出口、运营商）这些差异只有真机能覆盖。

## 已验证的接口事实

以下全部是在真实账号上跑通后确认的，不是推测。

| # | 请求 | 关键点 |
|---|---|---|
| 1 | `GET https://ca.csu.edu.cn/authserver/login?service=<urlencode(ecard 的 CAS 入口)>` | 入口 = `https://ecard.csu.edu.cn/berserker-auth/cas/login/wisedu?targetUrl=https://ecard.csu.edu.cn/plat-pc/?name=loginTransit` |
| 2 | 解析 **`id=pwdFromId`** 表单 | 取 `pwdEncryptSalt`（16 字节）、`execution`、`cllt=userNameLogin` |
| 3 | 加密密码 | AES-128-CBC / Pkcs7；key = salt(UTF-8)，iv = randomString(16)，明文 = `randomString(64) + 密码`，输出 base64 |
| 4 | `POST /authserver/login?service=…` | **必须带 `service`**；`password` = 密文；`passwordText` 要当 disabled 不提交 |
| 5 | 回调链 | `302 → ecard/berserker-auth/cas/login/wisedu → 302 → /plat-pc/?synjones-auth=<JWT>` |
| 6 | 业务请求头 | `synjones-auth: bearer <token>` 和 `authorization: bearer <token>`，`referer: https://ecard.csu.edu.cn/plat-pc/` |
| 7 | `GET /berserker-app/ykt/tsm/queryCard?scene=recharge&synAccessSource=pc` | `data.card[0].db_balance` 是余额（**单位：分**）；注意 `sno` / `name` 是**服务端脱敏**的（形如 `8********7`、`吕*远`），不能拿去和登录账号做全等比较 |
| 8 | `GET /berserker-search/search/personal/turnover?timeFrom=YYYY-MM-DD&timeTo=YYYY-MM-DD&size=100&current=1&synAccessSource=pc` | 缺 `synAccessSource` 返回 **405** |

### 流水字段（实测）

- `tranamt`：金额，**单位分，永远是正数**
- 方向只看 `typeId`：**`1` = 消费（支出），`2` = 充值（收入）**；`turnoverType` 分别是「消费」「充值」，`icon` 是 `consume`/`recharge`
- `cardBalance`：**交易后**余额（分）
- `effectdateStr` / `jndatetimeStr`：本地时间文本，如 `2026-09-28 12:02:13`
- `resume`：形如 `南校区学生宿舍内xzx洗浴-持卡人消费`，去掉 `-持卡人消费` 后缀才是商户名
- `toAccount`：最稳定的商户分组键（实测 `1000085`=洗浴，`3200010`/`3200015`/`3200002`/`3200003`=食堂，`0`=充值）
- `orderId`：唯一流水号，用于去重
- 日期格式用 `YYYY-MM-DD`；400 天区间一次请求即可返回全部（`size=100` 够用，仍实现了分页）

### 两个踩了很久的坑（务必保留注释里的说明）

1. **`cllt` 必须取 `pwdFromId` 表单里的 `userNameLogin`。**
   登录页里有 4 个表单（兼容/FIDO、短信动态码、账号密码、扫码），都用同一个 `name`。
   用正则抓「文档里第一个 `name=cllt`」会拿到 FIDO 表单的 `fidoLogin`，
   于是每次登录都变成「FIDO 登录且 `responseJson` 为空」，
   服务端返回 **401 认证失败**，而且**不计入密码错误次数**（`checkNeedCaptcha` 一直是 false），
   极易被误判成「密码错了」。正确做法是解析指定 id 的表单再按 DOM 顺序序列化。

2. **POST 的 URL 必须带上 `service` 参数。**
   站点 JS 用 `utils.setUrlParam("pwdFromId","?service",…)` 把它拼到 form action 上。
   少了它（例如 `new URL("/authserver/login", page.url)` 会把查询串丢掉）服务端直接 **500**。

### 加密实现已逐字节验证

`tools/verify-crypto.mjs` 把站点自己的 `encrypt.js`（内含 CryptoJS）载入 Node 的 `vm`，
与 Kotlin/Node 侧的实现用同一组 salt/iv/prefix 比对 6 种密码形态（纯数字、字母数字、
特殊符号、含中文、1 字符、16 字节边界），**结果全部一致**，随机字符集也一致（48 字符）。

> **踩坑记录**：这个 AOSP 模拟器的 SystemUI 有时会自己崩
> （`FATAL EXCEPTION: com.android.systemui … subscriptionId 1 is not in the list of valid subscriptions`），
> 崩了之后屏幕会卡住不刷新、`am start` 也像没生效、`pidof` 查不到进程。
> **这是模拟器自身的问题，与本 App 无关**（判断依据：崩溃日志里的进程是 `com.android.systemui`），
> `adb emu kill` 后重启模拟器即可恢复。
>
> **另一个坑**：`adb emu kill` 属于非正常关机 —— 实测重启后 **AVD 的 userdata 可能没保住**
> （App 包整个消失、需要重新 `adb install` 并重新登录），还会留下过期的 `multiinstance.lock`
> 和 `crashpad_handler` 残留进程。想保留 App 数据就别用 kill，
> 或者干脆每次都带 `-wipe-data` 从干净状态跑（反正数据能重新同步）。

注意：这个 AVD 是 **320x640 的小屏**（远小于真机），
上面第 2 个 bug（保存按钮被挤出屏幕）正是被它暴露出来的 —— 大屏真机上未必能发现。

## 扩展功能（第二阶段：多账户 + 微信/支付宝 + 多校）

### 已完成

**1. 多账户模型**
`accounts` 表 + 记录归属账户。校园卡余额由同步写入；微信/支付宝余额由用户手动维护
（`balance_manual` 标记区分）。数据库 v1 → v2 有迁移：老记录自动归入校园卡账户，
原来的余额 meta 搬进账户表，**老数据不丢**。

**2. 内部转账配对（避免重复计账）**
`TransferMatcher`：方向相反 + 金额精确相等（分）+ 时间在 ±2 小时内 + 账户不同 + 渠道一致。
配对后两条记录都标记为转账，`statCents` 记为 0 —— **计入各自账户余额，但不计入收支统计**。
不做这一步的话，「微信支出 + 校园卡充值」会让总收入和总支出双双虚增。

渠道判断依据是实测数据：校园卡充值记录的 `payName` 就是「微信支付转账」，
所以「微信 → 校园卡」这一对可以被确认，而不是靠猜。

**3. 多校适配器架构**
`data/school/SchoolProfile.kt` 把「地址 + 路径 + 表单/字段名」收敛成一份配置，
`data/school/CampusCardProvider.kt` 定义数据源接口。
- **同厂商（新中新 + 金智 CAS）的学校**：加一条 `SchoolProfile` 即可，代码不动
- **不同厂商**：实现 `CampusCardProvider` 接口并注册

`SchoolRegistry.ADAPTATION_CHECKLIST` 列出接入新学校要抓包确认的 7 项。
⚠️ 目前**只有中南大学是实测过的**，其他学校需要真实账号逐项验证——我没有别校账号，
所以这一条交付的是框架和清单，不是「已接通」。

**4. 通知监听自动记账（微信/支付宝）**
`notification/PaymentNotificationParser.kt` + `PaymentNotificationService.kt`。
- **不碰微信/支付宝的服务器**：只读系统投递的通知，不用账号密码、不逆向私有接口，无封号风险
- 解析规则**表驱动**，文案变了加一条正则即可
- **解析不出来不丢数据**：认不出金额的通知以「待确认」入库，原文保留，用户可手动补全
- 同一分钟内的重复通知按一条处理（通知会被更新重投）
- 渠道开关双保险：服务层和仓库层都会检查用户是否开启了该渠道

### 时区处理（已修复的一个隐患）

校园卡返回的是**服务端本地时间**字符串（北京时间，形如 `2026-09-28 12:02:13`），不带时区。

早先的实现按**设备时区**解析，于是设备时区一变（旅行、或模拟器默认 UTC），
所有同步记录的时间戳会整体偏移 8 小时，表现成「同步来的记录排到了今天手动记的记录前面」，
**而且内部转账的 ±2 小时配对窗口会因此完全失效**。

现在按**学校时区**解析（`SchoolProfile.timeZoneId`，中南大学为 `Asia/Shanghai`），
与设备设置无关。展示仍然直接用服务端给的字符串（就是学校的本地时间），不需要换算。
`SchoolTimeTest` 里有 7 项测试，包括一条「旧做法整整错 8 小时」的证明。

### 格式：CSV / XLSX / ZIP 都支持

- **ZIP**：微信账单就是加密 zip，用 zip4j 就地解密（`java.util.zip` 不支持加密包）
- **XLSX**：xlsx 本身就是 zip，所以解压层本来就能打开它，只差把里面的 XML 读成表格。
  自己写了个最小读取器（`XlsxReader`，只读纯文本单元格）——引 Apache POI 会给一个 9MB 的 App
  加上十几 MB 依赖，不值得。读完交给 `BillImporter.parseRows`，**和 CSV 走同一套表头映射**。
- CSV 与 XLSX 的差异只在「怎么变成二维表」，之后的表头定位、列名映射、方向判断完全共用。

### 对账：三层，不重复也不漏

| 层 | 判据 | 处理 |
|---|---|---|
| 一 | 交易单号已存在 | 跳过（同一份账单重复导入） |
| 二 | 同账户有时间相近的**待确认**（金额 0） | **补全它**：写金额/方向/商户，不新增记录 |
| 三 | 同账户 + 同方向 + 同金额 + 时间差 ≤2 小时 | 跳过（通知已经完整抓到过） |

第二层是这轮最有价值的：红包/转账的通知**没有金额**，账单里**有** ——
补全之后那条记录既拿到了金额，又保留了通知原文当上下文，用户不用自己删一条重复的。

**设备实测**：红包待确认（0 元）→ 导入含该笔的账单 →
`新增 0 条` + `补全 1 条待确认` → 同一条记录变成 `收入 | 8800 | 张三`，账本仍只有 1 条 ✓

## 官方账单导入（半自动）

### 能做到哪一步、做不到哪一步

用户的期待是「帮我把微信账单自动弄进来」。诚实的分界线是：

| 环节 | 能不能自动 | 说明 |
|---|---|---|
| 打开微信/支付宝 | ✅ | `getLaunchIntentForPackage` 跳主页 |
| 跳进「钱包 → 账单 → 下载账单」 | ❌ | 微信内部页面 `exported=false`，其他 App 起不来 |
| 导出后**文件到手** | ✅ 半自动 | 微信发到**邮箱**的加密 zip，点附件选「用我的账本打开」 |
| 解压（要密码） | ✅ | zip4j 就地解密，不用自己先解压 |
| 解析 + 入库 + 去重 | ✅ | 见下 |

所以流程是：**App 里点「打开微信」→ 照着 6 步点完 → 回邮件点附件选本 App → 输密码 → 完事**。

### 解析：不写死行数，按列名映射

微信账单前面有 17~18 行元信息、支付宝最多 23 行（数字来自
[double-entry-generator](https://github.com/deb-sig/double-entry-generator) 的源码）。
但**故意不照抄这些魔法数字**，而是找表头行（同时含「交易时间」和「收/支」）再按列名建索引，
别名兜住 `金额(元)/金额`、`交易单号/交易订单号` 这类差异。所以列顺序变了也不会崩。

其他细节：UTF-8 BOM、**GBK**（支付宝老账单）、CSV 引号里的逗号、「不计收支」与已关闭的行跳过。

### 去重分两层

| 层 | 判据 | 场景 |
|---|---|---|
| 一 | 交易单号当 orderId | 同一份账单重复导入 |
| 二 | 同账户 + 同方向 + 同金额 + 时间差 ≤2 小时 | 同一笔**通知已经抓到过**（两者 orderId 形态不同，光靠 id 挡不住） |

导入的历史流水在余额快照之前，所以**不会改变当前余额**（你填的余额本来就包含它们）。

**设备实测**：导入 CSV → `新增 3 条`（含红包 88 元，这是通知永远抓不到的那类）→
再导入一次 → `新增 0 条，其中 3 条之前已经导入过`；改用 zip → `来源：压缩包里的 bill-wechat.csv` ✓

### 依赖

新增 `net.lingala.zip4j:zip4j:2.11.5`（`java.util.zip` 不支持加密压缩包）。
APK 因此从 9.64 MB 涨到 11.69 MB。

> ⚠️ 造测试夹具时踩到的坑：zip4j 2.11 的 `ZipParameters` 里 **`isEncryptFiles` 默认 false**，
> 只设 `encryptionMethod = AES` 打出来的是明文包 —— 于是「密码错了要报错」那两个用例一直是
> 假通过。现在有一条自检用例直接断言 `fileHeader.isEncrypted`，专门盯这件事。

### 2. 有的微信/支付宝金额读不出来 —— 忽略词误伤

`IGNORE_KEYWORDS` 里有 **「优惠」**，而微信支付的通知常写「已支付 ¥12.00，已优惠 ¥1.00」
—— 整条通知在解析之前就被丢掉了，表现就是「有的支付读不出金额」。

修法是把忽略词分两类：

| 类别 | 词 | 生效条件 |
|---|---|---|
| 通知**类型**词 | 验证码、身份验证、登录提醒、安全提醒、余额/账单/还款提醒 | **一律忽略**（支付宝会在「支付宝」标题下发登录提醒 —— 标题可信 ≠ 内容是一笔钱） |
| 疑似出现在支付正文里的词 | 优惠、红包封面、更新、版本 | **只在来源不可信时**才忽略 |

另外给可信来源加了一档兜底：正文里孤零零一个 `12.00`（个别版本真这么写）也认；
来源不可信时不当金额（聊天里说「12.00」不会记账）。

### 3. 账单里的收入变成支出 —— 金额负号

`parseAmountCents` 早期**保留了负号**，于是「-25.00 + 支出」在统计里算出正数，方向就反了。
现在**一律取绝对值**：收支方向由「收/支」那一列说了算，金额里的正负号只是同一种写法的两种表达。

## 通知抓取还能怎么改进（第四轮）

### 先否掉一条走不通的路

> 「发现有微信消息后，直接去读手机文件找微信通知」

**不可行**：微信的通知内容存在 `/data/data/com.tencent.mm/`，Android 沙箱下任何 App 都读不到
（除非 root）。通知也不是以文件形式落盘的 —— 系统是通过 `NotificationListenerService`
把内容投递给监听的 App，而**这正是我们已经在用的通道**。所以没有「更好的读取方式」，只有
「把这条通道用得更充分」。

### 用得更充分的地方（已做）

| 改进 | 为什么有用 |
|---|---|
| 正文不再只读 `EXTRA_TEXT`/`BIG_TEXT` | 金额可能塞在 `SUB_TEXT`/`INFO_TEXT`/`SUMMARY_TEXT`/多行文本/ticker 里 —— 以前这些位置一律不看，认不出金额就白抓了 |
| 诊断记录带上**通知渠道 id** | 渠道比标题更硬：微信支付有独立渠道，和聊天消息不是一个渠道。排查和**渠道白名单**都靠它 |
| 渠道可以加入白名单 | 精确匹配渠道 id 即视为支付通知 —— 标题被版本改烂了也不影响。<br>默认空（渠道 id 因手机/版本而异），从诊断里一键添加。设备实测：加 `channel_id=2` 后库里即刻生效 |
| `onListenerConnected` 时处理 `activeNotifications` | 服务刚连上时下拉栏里还挂着的支付通知，顺手补上 |
| `onListenerDisconnected` → `requestRebind` | 国产 ROM 省电时会解绑监听，用户只看到「突然不记账了」，重绑让系统尽快接回来 |

## 第三轮真机反馈：三个问题

### 1&2. 微信退款 / 支付宝支出认不出金额

**原因**（两条叠加）：

- 这两类通知的**标题不在白名单里**（不是「微信支付」），正文也只写「12.00元」而没有 `¥` 符号；
  老规则只允许「发送方可信」时才认 `N 元` 这种写法 → 认不出金额 → 落成待确认
- 退款通知常写的「退款到账」「原路退回」当时不在平台措辞表里 → 整条被忽略

**修法**：

- 平台措辞表补上 `退款到账 / 退款 / 已退 / 退回 / 原路退`
- **命中平台措辞时也允许 `N 元` 写法**（发送方可信时同样允许）
- 代价：聊天里同时出现「支付成功」和金额时会被记成**待确认**（标 LOW 置信度）。
  这是有意的权衡 —— 宁可多一条待确认（你能一眼看到、能补全也能删），也不要漏掉真实收支。
  这条权衡写进了测试用例名里。

### 3. 待确认的无法确认（已实现）

点开一条「待确认」记录，现在会直接给你一张补全表单：

- 显示**原始通知内容**（比如 `[微信红包]恭喜发财`），你知道这笔是什么
- **支出 / 收入** 切换 + **金额输入框** + 分类
- 「保存金额并入账」→ 它就变成一条正常账目，`kind` 从「待确认」变成「收入/支出」
- **账户余额自动重算**（余额 = 快照 + 快照之后的流水，金额一进来就算进去了）
- 补完之后如果金额刚好和校园卡充值对上，还会**自动配成内部转账**

**设备实测**：待确认的 0 元记录 → 填 88 元收入 → 提示「已补全，余额已跟着更新」
→ 总资产 ¥100.00 变 **¥188.00** → 「待确认 1」芯片消失 → 数据库 `收入 | 8800 | 1 | 其他`

### 配套：复制诊断记录

万一还有认不出来的通知，诊断页多了「**复制诊断记录**」按钮：把最近 30 条通知的

## 抓取方式的整体评估（哪种架构更好）

通知监听是**尽力而为**的通道，它的天花板由微信/支付宝决定，不由我们决定：

| 限制 | 说明 |
|---|---|
| 红包/转账没有金额 | 微信本身就不在通知里写数额，读通知永远拿不到 |
| 文案随版本变 | 每换一个版本就可能需要补规则（所以才需要诊断页 + 白名单） |
| 依赖手机在线 | 通知没到、被系统杀、权限被撤，那一段就漏了 |

所以更好的架构是**两层**：

| 层 | 来源 | 特点 |
|---|---|---|
| 第一层（实时） | 通知监听 | 即时、免操作；不确定的落成「待确认」等你补 |
| 第二层（权威） | **官方账单导入（CSV/XLSX）** | 完整覆盖红包/转账/退款/手续费，带交易号可去重；需要手动导出一次 |

第二层目前**只有扩展点没有实现**（`addExternalEntry` + `EntrySource.IMPORT`）。
评估过的其他路子都不推荐：无障碍服务模拟点击（易触发风控封号、UI 一改就废）、
截图 OCR（要引入 OCR 引擎、准确率不稳）、读邮箱（为了记账读全部邮件，隐私代价不成比例）。

## 手动账户的余额：快照 + 流水

### 问题

真机反馈：「微信的余额不会根据流水变动，我估计支付宝也一样」。

**确实是错的**：老实现只存了用户填的那个数字，之后通知抓进来的收支只是加了记录，
余额纹丝不动 —— 那你填的余额第二天就是假的了。

### 现在的模型

```
当前余额 = 你填的快照 + 快照之后的每一笔流水
```

- 你在绑定中心填的是「**此刻**微信里看到的余额」，保存时**同时记下快照时刻**
- 之后这个账户的每笔收支（通知抓的、手动补的）都会自动加减
- **快照之前的流水不重复计入**（那些已经包含在快照里了）
- **删掉一笔记录，余额会跟着回退** —— 否则数字就假了
- 校园卡不走这套（它的余额由同步写入，本来就是权威值）

界面上显示「当前余额 ¥X」，并在与快照不同时说明「由你填的快照 ¥Y 加上之后的流水自动算出」。

**设备实测**：填快照 ¥100.00 → 记一笔 88 元收入到微信 → 总资产变成 **¥188.00** ✓

## 批量管理：清理误抓的旧记录

通知筛选修好之前抓进来的那批「待确认」记录得清掉，一条条点太折磨。所以：

- **「待确认 N」筛选芯片**：主页筛选栏里，有待确认记录时才出现，点一下只看这些
- **批量模式**：列表右上角「批量」→ 每行出现勾选框 → 全选 / 取消全选 → 「删除 N 条」
- **二次确认**：一次删几十条，误触代价太大（对话框里也提醒：如果里面有真实收支，建议先手动补记再删）
- **逐条留墓碑**：删掉的 id 进 `deleted_orders`，所以**同步和重复通知都不会把它们插回来**

**设备实测**：注入 3 条待确认 → 芯片显示「待确认 3」→ 筛选后「共 3 条」→ 批量全选 → 删除 3 条
→ 确认 → 提示「已删除 3 条记录」→ 数据库只剩手动那条、墓碑 3 条 ✓

## 通知记账的两次真机反馈（都改掉了）

### 问题 1：任何微信消息都被抓取记录

**根因不是"正则太松"，而是落库逻辑错了**：老代码把「解析不出来」和「跟支付无关」混为一谈，
服务里对**每一条解析失败的通知**都存成一笔「待确认」账目 —— 所以每条微信聊天消息都进了账本。
再叠加一个次要原因：金额正则 `N 元` 太宽松，聊天里"我转你 50 元"也能匹配。

修法（两处一起改才有效）：

| 改动 | 说明 |
|---|---|
| 解析结果改成三态 | `Ignore`（与支付无关，**什么都不记**）/ `NeedsReview`（像支付但缺金额）/ `Parsed` |
| **必须先有交易信号才谈金额** | 强信号：通知发送方是「微信支付/微信收款助手/支付宝」，或文本含「支付成功/已支付/收款到账/退款成功」等平台措辞；弱信号：「转账/红包/收款/付款/到账/零钱」 |
| 弱信号只认 `¥` 前缀金额 | 「转账 100 元」这种聊天说法不再被采信 |

已钉成回归用例（`PaymentNotificationParserTest`）：`我转你 50 元`、`每人 88 元`、`谁借我 100 元`、
`记得给我 ¥50`、`你转账给我了吗` —— **全部必须被忽略**。自检页也加了两个「噪音样本」按钮，
你可以直接在自己手机上验。

### 问题 2：红包、转账的通知里没有金额

这是**微信本身的行为**，不是 App 的 bug：红包/转账的通知只写「[微信红包]」「[转账]待收款」，
不带数额，所以任何靠读通知的方案都拿不到。现在的处理：

1. 这类通知会被识别出来，记成**「待确认」**（原文保留），提醒你去补
2. **手动补记现在可以选账户了** —— 以前手动记账只能记到校园卡，红包补记到微信这条路根本走不通
3. 彻底的办法是**官方账单导入**：微信「我 → 服务 → 钱包 → 账单 → 常见问题 → 下载账单」
   可以导出 CSV/XLSX，里面**包含红包和转账**，是唯一权威且完整的来源。
   扩展点已经备好（`addEntry`/`addExternalEntry` + `EntrySource.IMPORT`），解析部分还没写。

### 顺带修掉的可用性问题

- **以前只有手动记的能删**，通知误抓的记录删不掉 → 现在**任何记录都能删**，
  并且删除会留下**墓碑**（`deleted_orders` 表，DB v4），同步/重复通知不会把它插回来
- 记账对话框在小屏（320×640）上要滚动才够得到「保存」，而滚动常被输入框吃掉手势
  → 按钮改成**固定在底部**，分类/账户改成单行横向滚动
- 键盘弹起时会盖住底部按钮 → 加 `imePadding()` + `decorFitsSystemWindows = false`

### 设备验证（模拟器）

| 项目 | 结果 |
|---|---|
| 聊天消息 | ✅ 提示「这条通知与支付无关，会被直接忽略、不记账」 |
| 红包通知 | ✅ 「已记成『待确认』…这类通知本身不带金额，需要你手动补上」 |
| 手动补记选账户 | ✅ 提示「已记一笔（**微信**）」；数据库 `wechat \| 8800 \| 收入` |
| 删除任意记录 | ✅ 共 2 条 → 1 条；重启后仍是 1 条 |
| 墓碑 | ✅ `deleted_orders` 里有该 order_id，记录没有被插回来 |

## 定位：这是一个账本，不是校园卡工具

改名前叫「校园卡记账」，但它的主体功能是**账本** —— 校园卡只是数据来源之一。
现在桌面名称与各页标题都是「**我的账本**」。

### 主页 = 资产总览（不再只有校园卡余额）

- **总资产** = 所有**启用**账户余额之和
- 下列各账户明细（校园卡 / 微信 / 支付宝），手动维护的会标「· 手动」
- 未绑校园卡时：给出引导按钮，而不是摆一个空余额
- 手动维护的账户余额还是 0 时：提示去哪儿填
- 同步失败与频率限制的提示也在这张卡里（内联，不弹框）

### 密码策略：记住登录

用户的反馈是「每次进入都要重新输入密码 很麻烦」，所以：

- 注册/解锁后**记住登录**，重启、从后台回来都直接进
- **只有主动点「我的 → 立即锁定」才需要重新输密码**
- 会话标记持久化在 `meta`（有测试专门盯它跨重启保持）

> ⚠️ 诚实说明：这只是**界面层**的锁。账本数据库本身没有加密，
> 能拿到设备数据目录的人可以直接读库、也可以把会话标记改回去。
> 它防的是「手机被别人顺手拿到」，不是拿到设备数据的攻击者。
> 要做到后者得用密码派生密钥加密数据库，那是另一个量级的改动 —— 需要的话可以另开一轮做。

### 首次进入的权限引导

注册并解锁后，先经过一页权限引导（**一次性，可跳过**）：

| 项目 | 说明 |
|---|---|
| 通知使用权 | 必需（用于微信/支付宝自动记账）。逐项说明读什么、不读什么、是否上传 |
| 忽略电池优化 | 建议。不设的话后台可能回收监听服务，导致漏记 |
| 微信/支付宝的「新消息通知」 | 用户侧前提，App 控制不了，所以只做说明 |
| 网络访问 | 安装时已自动授予，只做告知 |

**刻意不申请 POST_NOTIFICATIONS**：本 App 自己不发送通知，用不上的权限就不要 ——
界面上也明确写了这一条。

## 入门流程：本机账号 → 按需绑定

### 为什么改

老流程**一进来就是校园卡登录**，把两件不同的事混成了一个：
「打开这个 App 的凭证」和「读取中南大学校园卡数据的凭证」。
结果是：没有校园卡账号的人根本进不去，而学校账号的密码也变成了 App 的锁。

### 现在的三段流程（后两步都可以跳过）

```
① 本机账号（注册 / 解锁）   ← App 的入口，只存在这台手机上
② 绑定校园卡（可跳过）      ← 想自动同步校园卡流水才需要；跳过状态会被记住
③ 主页                     ← 不绑定也能用：手动记账 + 微信/支付宝通知自动记账
```

### 本机账号的实现要点

| 事项 | 做法 |
|---|---|
| 存哪 | 手机本地的 SQLite（`local_account` 单行表），**不联网、不上传、没有服务器** |
| 密码怎么存 | PBKDF2-HMAC-SHA256，16 字节随机盐，**10 万轮**；明文永不落盘 |
| 为什么不用单轮 SHA256 | 手机丢了、数据库被拷走时，单轮哈希对离线爆破几乎不设防，弱密码几秒就出来 |
| 比对方式 | `MessageDigest.isEqual` 常量时间比较，避免从耗时差反推哈希 |
| 改密码 | 需要旧密码；**同时换盐**，旧哈希即使泄漏也不能复用 |
| 登录失败提示 | 用户名错与密码错**返回一模一样的文案**，不泄漏「哪个用户名存在」（且用户名不对时也照样走一遍哈希） |
| 找回密码 | **没有**。纯本地的代价，界面上明说了 —— 留了后门，锁就白上了 |

`LocalAuth` 是纯函数（不碰数据库），所以密码学部分可以直接用 JVM 测试覆盖（16 项）。

### 设备验证（模拟器，全新安装）

| 步骤 | 结果 |
|---|---|
| 全新安装后打开 | ✅ 显示**注册**界面（不是校园卡登录），带「只存在这台手机上 / 不是学校账号 / 没有找回密码」的说明 |
| 填表并创建 | ✅ 账号创建成功，自动进入「绑定校园卡」步骤 |
| 绑定页 | ✅ 标题为「绑定校园卡」，说明这一步可跳过，底部有「先跳过，稍后再绑定」 |
| 跳过 | ✅ 进入主页，显示「校园卡未绑定」+「去绑定校园卡」按钮（而不是空余额） |
| 数据库 | ✅ `campus_bind_skipped=1`；密码列是 PBKDF2 哈希 |
| 冷启动 | ✅ 回到**解锁**界面（要输自己设的密码），用户名自动带出 |
| 错误密码 | ✅ 内联提示「用户名或密码不正确」 |
| 正确密码 | ✅ 解锁后进入主页 |
| 再次冷启动 | ✅ 解锁后**直接进主页**，不再被拦回绑定页 |

### 验证过程中发现并修掉的问题

1. **跳过状态只存在内存里**：冷启动后又被拦回绑定页 —— 等于把「一进来只有校园卡登录」
   换个形式又犯一遍。改成持久化到 `meta`，并补了回归测试。
2. **未绑定时仍提示「点右上角同步」**：那时同步没东西可同步。空列表文案改为按绑定状态区分。
3 主页右上角的「退出」语义变成了「**锁定**」（不解绑校园卡，只是下次打开要重新输密码）。

### 页面结构与导航（第二轮补齐）

```
本机账号（注册 / 解锁）        ← 入口，只存在这台手机上
  ↓
绑定校园卡（可跳过，会记住）    ← 想自动同步校园卡流水才需要
  ↓
主页 ──→ 我的 ──→ 绑定中心 ──→ 通知权限、教程与自检
                 └─→ 绑定校园卡
```

- **主页顶栏只留「同步」和「我的」**：原来挤了「自动记账 / 同步 / 锁定」三个按钮，
  在窄屏上把标题挤成了两行。「自动记账」和「锁定」都收进了「我的」页。
- **「我的」页**：本机账号信息、**修改密码**（页内展开表单）、绑定状态一览、
  绑定中心入口、通知设置入口、「立即锁定」。
- **绑定中心**：校园卡（绑定 / 二次确认后解除绑定 / 显示学校与学号）、
  微信与支付宝（开关 + **余额手动录入**）。
  渠道开关和余额从「通知设置页」**搬到了这里** —— 那边只负责通知子系统自己的事
  （权限、教程、自检、内部转账重扫），避免两处重复。
- **导航**：`MainActivity` 里一个 `sealed interface Screen` + 一个 list 当返回栈。
  加新页面只需加一项 + 一个 `when` 分支，没有引入导航库（少一个依赖）。
- **动作集合**：`HomeActions` / `ProfileActions` / `BindingActions`。
  主页参数一度到 11 个，位置传参的坑踩过两次；收成对象之后，
  新增动作不改签名，调用方也必须写命名参数。

（另外**有意不重置频率限制**：退避与冻结冷却针对的是学校账号，解绑再绑不等于可以立刻重试。）

## 频率限制与风控冻结冷却

### 为什么必须有

中南大学的统一身份认证带风控。开发期间我反复跑联网测试，把账号触发了冻结：

> 该账号已被冻结，预计解冻时间：2026-09-28 15:44:30，冻结原因：**账号频繁访问**

所以限制不是「优化」，是**必须做的事**。

### 两条硬性设计约束

1. **必须在发出任何网络请求之前判断**。先登录、失败了再判断「是不是太频繁」是没用的 ——
   那次访问已经被服务端算进去了，而它正是触发风控的原因。
2. **冻结时间要照着学校的说法等**。学校已经明确给了「预计解冻时间」，
   继续重试只会延长冻结，所以直接冷却到那个时刻（再留 1 分钟余量，避免卡在解冻那一秒又踩风控）。

### 规则

| 规则 | 值 | 作用 |
|---|---|---|
| 两次登录尝试最小间隔 | 30 秒 | 防连点 |
| 24 小时内登录次数上限 | 20 次 | 防止长时间挂着刷 |
| 手动同步最小间隔 | 60 秒 | 防连点「同步」 |
| 自动同步间隔 | 6 小时 | 正常使用的后台更新 |
| 连续失败退避 | 1 → 5 → 15 → 60 分钟 | 密码错/被拦时逐级拉长 |
| 风控冻结冷却 | 到学校给的解冻时间 + 1 分钟 | 不再无谓重试 |

补充细节：
- **限制状态存在 `meta` 表里**，所以**重启 App 绕不过去**（有测试专门盯这一点）
- **只把「认证层面」的失败计入退避**（密码错、被冻结）。断网、超时不算 ——
  否则网络不稳的用户会被自己的退避规则锁住
- 冻结时间按**学校时区**解析（复用 `SchoolTime`），与设备时区无关

### 界面表现

被限制时：**同步按钮置灰**，余额卡里显示原因和还要等多久，例如

- 「⏳ 账号被学校风控临时冻结，19 分钟后可重试。这是学校对短时间内频繁登录的保护机制，不是 App 出错。」
- 「⏳ 登录太频繁，请 1 分钟后再试」

倒计时是活的（每次进页面/刷新都会重算）。

### 设备验证

这两个分支都是在模拟器上实测的，**验证方法本身也值得一提**：
我是直接往数据库 `meta` 表里注入限制状态（而不是真的去登录），
这样**全程没有发出任何网络请求**，也就不会因为验证而再次触发风控。

| 场景 | 结果 |
|---|---|
| 注入「冻结到 20 分钟后」 | ✅ 同步按钮置灰 + 显示冻结说明与倒计时（20 → 19 分钟） |
| 注入「刚刚登录过」 | ✅ 同步按钮置灰 + 显示「登录太频繁，请 1 分钟后再试」 |

这个过程还抓到两个真 bug（都已修）：
1. 冷启动时 `init` 没填限制状态，导致**距上次同步不到 6 小时（不触发自动同步）时界面完全不显示限制** ——
   因为只有 `refresh()` 里算了这个值，而那条路径根本没被走到。
2. 限制判断只看了「同步层面」（60 秒间隔），漏了「登录层面」（最小间隔/失败退避/每日上限），
   于是界面显示「可以同步」、点下去才被拦住。现在两者都算，界面与实际行为一致。

## 已知限制（如实说明）

1. **没有在真机或模拟器上跑过** —— 本机没有 adb、没有连接设备、没有模拟器，
   只能保证「编译通过」。安装到手机上首次运行的验证需要你来做。
2. **自动分类是启发式规则**，依据是实测 56 条流水里的商户名和 `toAccount`。
   能覆盖食堂/洗浴这类主要商户，但新商户会落到「其他」，需要手动改。
   另外有一批小额消费（宿舍水控等）服务端 `resume` 恰好就是「持卡人消费」、没有商户名，
   这类会显示为「校园卡消费」而不是拿「持卡人消费」当商户名。
3. **接口随时可能变** —— 学校前端是「新中新 校园一卡通」，版本号 `1.07.fix`。
   若同步失败，按本文档第 2 节的流程重新抓一遍路径与字段即可。
4. **同步范围**默认 365 天，最多 30 页 × 100 条。
5. **收入/支出判定**依赖 `typeId`（1/2）。目前实测只有「消费」和「充值」两类，
   若出现退款等新类型，`EcardApi.queryTurnover` 里有兼容关键词，但仍需实测确认。

## 为什么列表里没有华南师范大学

2026-10 试过接入，**四个入口全部走不通**，结论记在这里，免得后来者再花一晚上：

| 入口 | 结果 |
|---|---|
| `ecard.scnu.edu.cn` / `ecardhall.scnu.edu.cn`（一卡通服务大厅，PC 端） | 同一台服务器，**HTTP 403**，说明是**校内 IP 限制**，校外访问不了 |
| `webvpn.scnu.edu.cn` | 公网 TCP 443 能连，但 **TLS 握手被强制关闭**，校外用不了 |
| `sso.scnu.edu.cn`（统一身份认证） | **公网可达**，但里面**没有一卡通入口** |
| `ecardwx.scnu.edu.cn`（微信版） | 唯一可用的入口，但登录是**微信公众号网页授权**（302 → `open.weixin.qq.com`），凭据是微信侧 openid |

**为什么微信那条也不行**：`snsapi_base` 授权只有微信客户端能完成，第三方 App 打开的同一网址只会得到"请在微信客户端打开"；而且就算用户自己在微信里登进去，App 也读不到微信的 cookie（那是另一个应用的数据）。

**理论上还能走的路**（需要人工抓包，本项目尚未实现）：

1. 在能访问的环境里（校内网络，或微信 PC 版内置浏览器）登录一次，抓到**流水接口的 URL + 认证字段**，
   然后由用户**粘贴 token** 到 App 里 —— token 不认人只认票，校外也能用，过期再抓一次即可
2. 这条路的通用形态是「自定义院校 + Token 粘贴绑定」，`SchoolProfile` 已经预留了
   `loginKind` 维度（`CAS_FORM` / `WECHAT_OAUTH`），将来加第三种 `TOKEN_PASTE` 即可

**在那之前，华师用户可用的路径**：手动记账 + 通知记账（微信/支付宝给校园卡**充值**时的通知能自动进账；
校园卡**消费**是卡内扣费，不会出现在微信/支付宝账单里）。
